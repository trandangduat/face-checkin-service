# Giảm chi phí đọc và so khớp gallery

Nguyễn Quang Bảo Sơn · 23021685 · Phase 2

## Đường đi của một request

1. [`CheckInService.check_in()`](../app/services/check_in_service.py#L32) gọi embedder và chuẩn
   hóa probe. Ví dụ vector thô `[3, 4]` từ model `buffalo_s` trở thành `[0.6, 0.8]`.
2. Service gọi [`FaceProfileRepository.list_candidates()`](../app/domain/ports.py#L44) với model
   `buffalo_s` và dimension `2`. Store mặc định lọc `list_all()` theo model và shape, giữ thứ
   tự sẵn có của store.
3. [`SQLAlchemyFaceProfileRepository.list_candidates()`](../app/repositories/face_profile_repository.py#L38)
   dùng `WHERE model_name = ... AND embedding_dim = ... ORDER BY id`. Mapper chỉ đọc BLOB
   của hàng SQL trả về. API danh sách profile tiếp tục gọi `list_all()`.
4. Với hai ứng viên ID 5 và 9 có vector cũ `[6, 8]` và `[0, 2]`, service dùng
   [`normalize_embedding()`](../app/domain/embeddings.py#L6) cho từng vector, rồi nhân ma trận
   với probe. Cosine lần lượt là 1 và xấp xỉ 0,8. ID 5 thắng và check-in được lưu với
   `SUCCESS` nếu điểm đạt ngưỡng.

Không có ứng viên thì service lưu `UNMATCHED` với score `None`. Điểm dưới ngưỡng được lưu
cùng `UNMATCHED`. Vector ứng viên zero hoặc NaN vẫn gây `FaceEmbeddingFailed` trước khi ghi
check-in. Nếu embedder không thấy mặt, service ghi `NO_FACE` rồi trả lỗi tương ứng. Thêm hoặc
xóa profile được nhìn thấy ở request kế tiếp sau khi thay đổi đã commit vào DB.

## Quyết định kỹ thuật và giới hạn

Đưa bộ lọc vào SQL giúp DB chỉ gửi BLOB tương thích cho ORM. Gallery thuần vẫn phải trả đủ
vector. Truy vấn chưa có index ghép model/dim, nên DB vẫn có thể quét bảng. Với `K` ứng viên
và `D` chiều, cosine exact tốn `O(KD)` phép tính và bộ nhớ ma trận `O(KD)`.

Thử chuẩn hóa `float32` theo hàng bằng `np.linalg.norm(matrix, axis=1)` làm hỏng 4 test
ngưỡng trên NumPy 2.2.6/macOS ARM64. Ví dụ score cũ `0.02106933295726776` xuống còn
`0.021069321781396866`. Với ngưỡng đúng bằng score cũ, kết quả đổi từ chấp nhận sang từ chối
dù sai số chỉ khoảng `1.12e-8`. Bản giao dùng nguyên phép chuẩn hóa cũ cho từng hàng và vẫn
tính toàn bộ cosine bằng phép nhân ma trận. `argmax` chọn cực đại đầu tiên sau khi clip
về `[-1, 1]`. Không cần cache, migration hay dependency mới.

## Bốn câu hỏi vấn đáp

1. **Có cải thiện độ phức tạp tìm kiếm không?** Cosine exact vẫn `O(KD)`. SQL giảm số
   hàng và byte BLOB trả về. DB còn có thể quét bảng vì chưa có index model/dim.
2. **Hai người cùng điểm nhận diện thì chọn ai?** Với adapter SQL, profile có ID nhỏ hơn
   thắng. SQL sắp ID tăng và `argmax` chọn cực đại đầu tiên. Test dùng hai ID có vector giống nhau.
3. **Vì sao score gần nhau vẫn phải so quyết định?** Sai số float32 có thể đổi ứng viên thắng
   hoặc làm điểm rơi xuống dưới ngưỡng. Probe block chênh khoảng `1.12e-8` nhưng đã đổi quyết
   định, nên code giao giữ phép chuẩn hóa theo từng vector.
4. **Xóa profile có cần invalidation không?** Không. Mỗi request gọi lại repository và đọc
   dữ liệu DB. Test thêm rồi xóa profile và kiểm kết quả ở request kế tiếp.
